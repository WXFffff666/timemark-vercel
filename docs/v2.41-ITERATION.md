## 一、探索结论

- **alert() 96 处**（v2.40 账本只记了 2 处——当时只盘了 confirm）：Settings 38、Security 11、EventForm 11、Channels 10、TriggerLogs 6、其余零散；其中错误型 59、成功型 16。原生 alert 与 R18 清零 confirm 后的统一弹窗体系割裂，是全站最后一大交互债。
- **audit「零 UI」为误报**：Security.tsx:483 已有操作审计卡（v2.27 F45）——纠正 v2.40 探索结论。
- **/api/v1 公共面 6 端点**：GET events、GET events/:id、GET expiry、GET habits、GET stats/daily、POST events（tmt_ token 鉴权）——OpenAPI spec 的实际范围。
- patterns/mcp/agent-health 为内部/机器接口，无需浏览器 UI（如实记录，不做无效 UI）。
- TODO/FIXME 全仓仅 2 处且为常量名，无技术债标记。
- OCR 建证件：现在一律 kind:'other'，未利用 fields（issuer→issuer、date→issuedAt）。

## 二、调研结论

- **Hono OpenAPI 两路**（[hono 官方](https://hono.dev/examples/zod-openapi)、[社区共识 2026-01](https://github.com/orgs/honojs/discussions/4621)）：`@hono/zod-openapi` 需全部路由改 OpenAPIHono（868 端点不现实）；`hono-openapi` 中间件也需路由级 schema。**定案：手工精选 /api/v1 六端点的 OpenAPI 3.1 spec**（公共 API 本就是门户文档对象），静态 JSON + ApiPortal 展示，零新依赖。
- **Toast 模式**（Sonner 式）：模块级 store + Host 组件挂 App 根部，`toast.success/error()` 全局函数，自动消失+堆叠+role=alert 无障碍。零依赖自建（~80 行），不引第三方。

## 三、三轮计划

### R20（第一轮：全站通知体系）

### R21（第二轮：API 门户文档化）

4. 打分（必须 > R20）。

### R22（第三轮：智能增强 + 收敛）

3. 收敛自查：前后端测试 / tsc / build / 真浏览器冒烟 / alert 与 confirm 双清零验证。
4. 终审打分（必须 > R21）；账本收官 + 记忆 + 推送部署。
